# SealDice 公骰监控系统需求分析

## 1. 文档状态

- 阶段：需求分析初稿
- 目标系统：Ubuntu + SealDice + Yogurt + Milky
- 通知方式：电子邮件，依靠手机邮箱客户端及时提醒
- 核心原则：监控服务必须独立于 SealDice 和公骰 QQ 会话运行

## 2. 背景

公骰通过 Yogurt 提供的 Milky 协议接入 QQ。QQ 会话可能因为风控、网络、登录态
失效等原因掉线，而 SealDice 自身不能可靠识别所有“协议端仍运行、QQ 实际已离线”
的情况。

公骰投入公开使用后，除了连接可用性，还需要掌握好友申请、群邀请、实际加入或
离开群聊、聊天插件 Token 消耗等运营信息。

使用公骰 QQ 自身发送掉线告警不可行，因为掉线时已经失去发信能力。因此系统采用
独立 SMTP 邮件作为告警通道。

## 3. 建设目标

系统应当：

1. 区分 QQ 会话、Yogurt、SealDice 三个层次的故障。
2. 在关键故障发生和恢复时及时发送邮件。
3. 可靠记录好友申请、群邀请和群列表变化，重启后仍可追溯。
4. 汇总聊天插件 Token 用量并按阈值预警。
5. 对重复事件去重，避免故障期间产生邮件轰炸。
6. 在 Ubuntu 上作为独立常驻服务运行。

## 4. 用户与角色

### 4.1 骰主（系统管理员）

- 接收实时告警、业务提醒和日报。
- 根据邮件信息登录 SealDice 或 QQ 进行人工处理。
- 配置、更新、备份和维护监控系统。
- 后续版本可通过管理界面查询历史记录。

### 4.2 公骰用户

- 向公骰提交好友申请。
- 邀请公骰进入群聊或使用聊天插件。
- 不直接访问监控系统。

## 5. 系统边界

### 5.1 第一期包含

- Milky WebHook 接收与鉴权。
- `bot_offline` 事件检测。
- Yogurt HTTP API 健康检查。
- SealDice 进程或 HTTP 健康检查。
- 好友申请实时事件与定时补偿查询。
- 群邀请实时事件。
- 群列表快照对比，发现新增群和移除群。
- Token 用量接收、汇总和阈值告警。
- SMTP 邮件队列、重试、去重和恢复通知。
- SQLite 持久化。
- GitHub Release 版本检测、手动更新和可选自动更新。
- systemd 部署与日志管理。

### 5.2 第一期不包含

- 好友申请和群邀请的审批；该能力继续使用 SealDice 自带功能，监控系统只记录和提醒。
- 自动退群、封禁用户或修改群配置。
- 无限自动重启、自动扫码或绕过 QQ 风控。
- 完整 Web 管理后台。
- 保存完整聊天内容。

## 6. 功能需求

### FR-01 Milky 事件接收

- Yogurt 向监控服务的本地 WebHook 推送 Milky 事件。
- 监控服务校验 WebHook Authorization Token。
- 原始事件在处理前写入数据库。
- 使用稳定的事件指纹去重。
- 无法识别的事件应记录但不得导致服务退出。

### FR-02 QQ 掉线与恢复检测

- 收到 `bot_offline` 后立即将 QQ 状态设为离线。
- 邮件中包含发生时间、账号、下线原因和检测来源。
- Yogurt HTTP 接口正常不能单独作为 QQ 在线的证据。
- 主动检查连续失败三次后才确认故障。
- 恢复后发送一次恢复邮件，并包含故障持续时间。
- 同一故障在恢复前只发送一次严重告警。

目标时效：

| 场景 | 目标发现时间 |
|---|---:|
| 收到 `bot_offline` | 5 秒内 |
| Yogurt HTTP 不可用 | 90 秒内 |
| SealDice 不可用 | 90 秒内 |
| 状态恢复 | 60 秒内 |

### FR-03 Yogurt 状态检测

- 定时调用只读 Milky API 检查 HTTP 服务。
- 可选读取 systemd 或 Docker 的服务状态。
- 区分超时、拒绝连接、鉴权失败和 API 错误。
- 记录连续失败次数、最近成功时间和响应耗时。

### FR-04 SealDice 状态检测

- 首选 SealDice HTTP/WebUI 健康地址。
- 如果没有合适的 HTTP 检查，使用 systemd/Docker 进程状态。
- 检测 SealDice 存活但无法连接 Yogurt 的情况。
- 故障及恢复分别通知一次。

### FR-05 好友申请监控

- 处理 Milky `friend_request` 事件。
- 保存申请人 QQ、UID、验证信息、来源、发生时间和处理状态。
- 启动时及之后每五分钟查询待处理申请，用于补偿服务停机期间遗漏的事件。
- 同一申请只通知一次，状态改变后允许再次通知。
- 邮件不得自动触发同意或拒绝动作。

### FR-06 群邀请和群变化监控

- 处理 `group_invitation` 事件并立即通知。
- 保存群号、邀请序号、邀请人 QQ、来源群号和时间。
- 定时获取群列表并与上次成功快照比较。
- 发现新群时发送“已进入新群”邮件。
- 发现群消失时发送“已离开群”邮件，原因未知时不得臆测为被踢。
- 尽可能将邀请事件与实际入群事件关联。

### FR-07 Token 用量统计

- 首选从聊天插件或模型 API 响应的 `usage` 字段获取用量。
- 如果插件无法上报，可在插件与模型服务之间增加本地统计代理。
- 日志解析仅作为最后的兼容方案。
- 每次调用可记录：时间、提供商、模型、输入 Token、输出 Token、缓存 Token、
  推理 Token、总 Token、成功状态、耗时、群号和用户 QQ。
- 默认不保存用户的完整提问和模型完整回答。
- 支持按天、模型、群和用户汇总；只有数据源能够关联时才启用群/用户维度。
- 支持日额度 50%、80%、95% 阈值告警。
- 每日生成一封用量日报。
- 费用只作为估算值，必须配置带生效日期的模型价格表。

### FR-08 邮件通知

- 使用 SMTP over TLS 或 STARTTLS。
- 使用邮箱应用专用密码，不使用主账号密码。
- 支持一个或多个收件地址。
- 邮件先入持久化队列，成功发送后再标记完成。
- 发送失败采用指数退避重试，并设置最大重试间隔。
- 严重故障、恢复、业务提醒、用量预警和日报使用不同主题前缀。

建议主题：

```text
[严重][公骰监控] QQ 已掉线
[恢复][公骰监控] QQ 已重新上线
[提醒][公骰监控] 收到好友申请
[提醒][公骰监控] 被邀请加入新群
[用量][公骰监控] Token 已使用 80%
[日报][公骰监控] 2026-09-18 运行报告
```

### FR-09 通知抑制和升级

- 同一资源、同一故障类型、同一故障周期只发送一次。
- 恢复事件关闭当前故障周期。
- Token 每个阈值每天只通知一次。
- 普通事件允许在短时间窗口内合并。
- 邮件队列堆积或 SMTP 连续失败应写入本地严重日志。

### FR-10 数据查询与日报

- 每日汇总服务可用性、故障次数、好友申请、群变化和 Token 用量。
- 日报生成失败不得影响实时监控。
- 第一期通过 SQLite 和日志查询；管理界面留待后续版本。

### FR-11 GitHub 更新检测与更新

- 项目发布到 GitHub 后，以 GitHub Release 作为正式版本来源，不直接自动跟随默认分支提交。
- 定时检查最新稳定 Release，默认每六小时一次，并支持手动立即检查。
- 发现新版本时发送邮件，包含当前版本、目标版本、发布时间和变更摘要。
- 支持三种配置模式：仅通知、手动安装、自动安装。
- 默认模式为“仅通知/手动安装”；必须由骰主显式开启自动安装。
- 手动更新提供命令行入口，至少支持检查、安装指定版本、查看当前版本和回滚。
- 自动更新只允许安装符合配置更新通道的正式版本，预发布版本默认忽略。
- 下载的发布包必须校验发布清单中的 SHA-256；校验失败时禁止安装。
- 更新前保存当前程序版本和必要元数据，但不得覆盖配置、数据库和密钥文件。
- 更新过程使用独立更新助手执行：下载到临时目录、校验、解包、停止主服务、原子切换、
  启动并健康检查。
- 新版本在限定时间内未通过健康检查时，自动切回上一版本并发送失败邮件。
- 数据库迁移必须有明确版本，并在发布前验证回滚兼容性；无法安全回滚的更新不得自动安装。
- GitHub 不可访问、API 限流或下载失败不得影响监控主功能。
- 私有仓库如需 Token，Token 只能通过环境变量或受限权限的秘密文件提供。
- 所有检查、下载、安装、回滚动作均记录审计日志。

## 7. 数据需求

建议数据实体：

| 实体 | 用途 |
|---|---|
| `raw_events` | 保存收到的原始 Milky 事件及事件指纹 |
| `service_states` | 保存 QQ、Yogurt、SealDice 当前状态 |
| `incidents` | 保存一次故障从发生到恢复的完整周期 |
| `friend_requests` | 保存好友申请及处理状态 |
| `group_invitations` | 保存群邀请 |
| `group_snapshots` | 保存群列表快照和变化 |
| `token_usage` | 保存单次模型调用用量 |
| `notification_outbox` | 保存待发送、重试及已完成邮件 |
| `daily_statistics` | 保存日报聚合结果 |
| `update_history` | 保存版本检查、安装、健康验证和回滚历史 |

默认保留策略：

- 原始事件：90 天。
- 运行故障和每日汇总：长期保留。
- 单次 Token 记录：180 天，汇总长期保留。
- 完整聊天内容：不保存。

## 8. 非功能需求

### 8.1 可靠性

- 监控服务重启后继续处理未发送邮件。
- WebHook 处理先持久化、后执行业务逻辑。
- 定时任务失败不得导致其他任务停止。
- 数据库写入应使用事务。

### 8.2 安全性

- Yogurt、监控服务和数据库默认仅允许本机访问。
- Milky API Token、WebHook Token 和 SMTP 密码不得进入日志或数据库。
- 配置文件权限应限制为服务用户可读。
- 管理接口如果后续开放，必须单独鉴权。
- 更新器只能接受配置中指定的 GitHub 仓库及发布资产，禁止从事件参数拼接任意下载地址。
- 自动更新不得修改 SMTP 密码、Milky Token、数据库或用户配置。

### 8.3 可维护性

- 外部系统通过适配器接口隔离。
- 业务规则不得直接依赖具体邮箱或聊天插件。
- 日志采用结构化字段，包含事件 ID 和故障 ID。
- 支持配置化调整检查周期、阈值和数据保留时间。

### 8.4 性能

- 预期事件量较低，单进程异步服务足够。
- WebHook 正常情况下应在一秒内完成持久化并响应。
- 邮件发送不得阻塞 WebHook 接收。

## 9. 邮件内容要求

严重故障邮件至少包含：

- 公骰账号。
- 故障对象和故障类型。
- 首次发生时间。
- 检测来源。
- Yogurt 与 SealDice 的当前状态。
- 原始原因的安全摘要。
- 是否需要人工处理。

恢复邮件至少包含：

- 恢复时间。
- 故障持续时间。
- 恢复检测来源。
- 故障期间通知次数。

## 10. 验收标准

### AC-01 QQ 掉线演练

模拟 `bot_offline`，五秒内生成一条故障记录并进入邮件队列；重复事件不重复发信。

### AC-02 恢复演练

恢复 QQ 连接后一分钟内生成恢复邮件，包含正确的持续时间。

### AC-03 好友申请

实时事件和补偿查询得到同一申请时，数据库只有一条业务记录和一封提醒邮件。

### AC-04 群变化

群列表新增或减少时只产生一次对应通知，且未知原因不会被描述为确定的“被踢”。

### AC-05 Token 统计

给定一组模拟调用，可正确计算每日、模型、群和用户汇总，并在跨越阈值时仅告警一次。

### AC-06 SMTP 故障

SMTP 暂时不可用时事件不丢失；服务重启并恢复 SMTP 后能够继续发送。

### AC-07 更新检查与手动更新

给定一个高于当前版本的模拟 Release，系统能发现并通知；执行手动更新后版本切换成功，
配置和数据库保持不变。

### AC-08 自动更新失败回滚

模拟新版本启动失败，更新助手能恢复上一版本、重新启动服务并记录回滚结果。

## 11. 已知限制

- 本机监控可以发现 QQ、Yogurt 和 SealDice 故障，但整台 Ubuntu 宕机或断网时无法从
  本机发送邮件；要覆盖该场景需要外部存活检查。
- `get_login_info` 成功不等于 QQ 一定在线，必须结合离线事件和主动检查。
- Token 明细能力取决于聊天插件和模型提供商返回的数据。
- QQ 风控、冻结、验证码和扫码登录必须由人工处理。

## 12. 远期设想：手机 App

手机 App 暂不进入第一期和第二期实施范围，仅保留架构扩展方向。其目标可能包括：

- 直接接收监控事件、故障告警和 Token 用量通知。
- 查看 QQ、Yogurt、SealDice 和监控服务状态。
- 在 QQ 掉线并需要重新登录时，安全获取当前登录二维码，便于骰主在外处理。
- 查看好友申请、群邀请和群变化，但审批仍优先复用 SealDice 现有能力。
- 使用推送通知替代或补充电子邮件。

该设想与 SealDice WebUI 功能存在明显重合，正式立项前应先评估能否通过 WebUI 的移动端
适配或安全代理满足需求，避免重复建设。

远程二维码涉及高敏感登录凭据，未来实现时至少需要：

- 独立身份认证和设备绑定。
- 端到端加密传输或等效保护。
- 二维码短时有效、只允许查看一次并禁止长期存储。
- 操作审计、会话撤销和设备丢失处置。
- 服务端不得将二维码写入普通日志或邮件。

## 13. 分期建议

### 第一期：可靠监控

- 掉线、恢复、好友申请、群变化、Token 统计和邮件通知。
- SQLite、systemd、通知去重和补偿查询。

### 第二期：项目运维

- GitHub Release 检测。
- 手动更新。
- 经过多版本演练后的可选自动更新与失败回滚。

### 第三期设想

- 手机 App、推送服务和远程二维码。
- 是否实施以 SealDice WebUI 当时的移动端能力为准。

## 14. 待确认事项

1. Yogurt 的具体版本，是普通 Yogurt 还是 Yogurt-PMHQ。
2. Yogurt 由 Docker、systemd 还是 SealDice 内置启动。
3. SealDice 的版本和可用健康检查地址。
4. 发件邮箱服务商、SMTP 模式和收件地址数量。
5. 聊天插件名称、版本、模型提供商及其是否返回 `usage`。
6. Token 配额是按金额、总 Token 还是提供商账户余额设定。
7. 日报发送时间和时区。
8. GitHub 仓库地址、Release 资产命名和稳定版/预发布版策略。
